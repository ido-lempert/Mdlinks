The dashboard that lied: dual writes, one crash, and the outbox pattern

Before you read

Frameable is a fictional company and the outage story is invented. The failure mode it illustrates - the dual-write problem - is real and well documented. No claim is made about any real product, customer, outage, or personal production experience.

The story

Frameable sells a stories widget: marketing teams publish tales from a dashboard, and a JavaScript SDK renders them on customer sites. Their stack is ordinary - a Node API, a SQL database, and a queue that fans events out to the cache invalidator and the dashboard's live feed.

At 02:11 on a Tuesday, a routine deploy restarts the API. One request is in flight: an editor clicked Publish on the launch tale. The endpoint does two things: it commits the tale's new status in the database, and it posts a tale.published event to the queue so every other part of the system hears about it. The process dies between those two writes.

The database now says published. The queue never heard a thing. The status badge on the dashboard reads straight from the tales table, so it happily shows "Published". But the dashboard's live feed - projected from queue events - never gets the event, and the cache invalidator never runs, so customer sites keep serving the old tale. At 09:04 the editor opens a ticket: "the badge says published, but the feed shows nothing and the site still shows yesterday's story." Nothing is lying, exactly. Each part is reading the only truth it has. There are two truths now.

The dual-write problem

Any endpoint that writes to two independent systems has this window. With independent local transactions and no distributed coordinator, a database commit and a queue publish cannot be made atomic - they are two systems with two transaction logs. Whichever write runs second can lose the race against a crash, a deploy, a network cut, or an OOM kill. Commit first and the event can be lost. Publish first and you get the mirror-image bug: an event describing a row that never committed.

The fixes people reach for first do not close the window. Retrying the queue publish helps with a flaky queue but not a dead process. Publishing before commit trades lost events for phantom events, which are worse. Distributed transactions (2PC/XA) offer real atomicity at the price of a coordinator, long lock holds, and a protocol many brokers do not support.

The pattern

The transactional outbox removes the second system from the request path. The endpoint performs one transaction against one database: update the business row, and insert a row into an outbox table in the same commit. Atomicity comes from the database itself - one transaction, one commit, both rows or neither. A separate relay process then reads unpublished outbox rows, posts them to the queue, and marks them published.

After commit, the outbox row is durable intent. In the demo it survived the API process self-terminating (process.exit(1)) immediately after COMMIT and was delivered later. That is the tested claim - an abrupt exit at the marked point, not a SIGKILL or a power loss. Around it are the usual production conditions: the database must actually be durable, the relay must keep retrying, the broker must acknowledge and retain messages, and ordinary operational failures can still delay delivery.

Delivery to the queue is at-least-once, not exactly-once. If the relay dies after the broker acknowledges a message but before it marks the outbox row published, the row is posted again on the next pass. Mark only after the broker's acknowledgement - and even then the crash window exists, so consumers must be idempotent. An ack timeout is another duplicate source: the relay cannot tell whether the broker stored the message, so it retries, and the consumer must absorb the repeat. That is part of the pattern, not an optional extra.

A runnable proof

The failure and the fix were built as real processes against a real file-backed database and crashed on purpose. One honest shortcut: the "queue" in the demo is an events table in the same SQLite file, a stand-in broker chosen so the demo runs with zero dependencies. The crash windows are the processes self-terminating at injected points via process.exit(1) - deterministic and abrupt (no cleanup code runs), but not an externally delivered SIGKILL or a power loss, so OS-level crash behavior is out of scope. What a table cannot show either is a broker with its own network failure modes. TypeScript on Node 22.23.4, built-in node:sqlite, run with node --experimental-strip-types. Four scenarios, eight assertions, all passing.

Phase A (the bug): the naive endpoint commits, then exits before the queue write - the harness asserts the crash really happened (non-zero exit code) and the queue is empty afterwards; the database says published, the dashboard has nothing. Phase B (the outbox): the process exits immediately after COMMIT, the outbox row survives, the relay delivers, the dashboard converges with zero loss. Phase C (the duplicate): the relay exits after queueing but before marking; the next run re-posts; the consumer's processed-event ledger, checked inside the same BEGIN IMMEDIATE transaction as the insert, skips the duplicate (duplicatesSkipped=1), and a deliberately non-idempotent applied_count stays 1 instead of 2 - proof the dedupe changes state, not just bookkeeping. Phase D (concurrent consumers): two consumers run against 50 queued events; the database opens with busy_timeout = 5000 so a consumer hitting the write lock waits instead of crashing - a finite wait covering this demo's contention, not a general guarantee. Measured: both exit 0, each event's effect is applied exactly once (per event ID - not an ordering or general exactly-once-delivery claim), and the 50 losing attempts are clean ledger skips.

The write path (tested, from the demo)
db.exec('BEGIN IMMEDIATE');
db.prepare(`UPDATE tales SET status='published' WHERE id=?`).run(taleId);
db.prepare(
  `INSERT INTO outbox(id, tale_id, type, payload, created_at)
   VALUES (?, ?, ?, ?, ?)`
).run(eventId, taleId, 'tale.published', JSON.stringify({ taleId }),
       new Date().toISOString());
db.exec('COMMIT');   // both rows commit, or neither does

The consumer's idempotency is one ledger table: inside the same transaction that updates the dashboard projection, it checks the processed ledger for the event id and inserts the id before committing. A duplicate is caught by the ledger lookup; the primary key is the backstop.

Postgres relay (illustrative, not run here)
-- illustrative Postgres relay query (not executed for this article)
SELECT id, type, payload
FROM outbox
WHERE published_at IS NULL
ORDER BY created_at
LIMIT 100
FOR UPDATE SKIP LOCKED;

SKIP LOCKED does not prevent duplicate delivery (a relay can still crash after posting and before marking) and does not by itself guarantee ordering - it only stops concurrent relays from double-handling the same row while the lock is held, inside that transaction - and the mark-published UPDATE must share that transaction for the lock to protect the claim-process-mark cycle. Per-aggregate ordering still has to be designed: single relay, partitioning, or sequence numbers in the payload plus consumer-side enforcement that rejects or buffers stale events.

The browser half

The dashboard's live feed is a small EventSource listener over server-sent events:

// illustrative browser code (not executed for this article)
const events = new EventSource('/api/dashboard/stream');
events.addEventListener('tale.published', (e) => {
  const { taleId } = JSON.parse(e.data);
  updateFeedRow(taleId, 'published');
});

SSE by itself is not durable replay. If the browser disconnects and misses an event, the stream alone does not guarantee it will arrive. You need a catch-up path: refetch the feed on reconnect, or use the Last-Event-ID header with a server-side cursor/replay buffer. And keep the three states separate: the committed database row, the delivered queue event, and what a user's screen currently shows. The outbox aligns the first two; the consumer plus a correct SSE/retry story closes the gap to the third.

What the outbox does not give you

Not exactly-once delivery: at-least-once plus idempotent consumers gets effectively-once application of each event - and only for effects that commit atomically with the ledger row; a side effect that already left the building (an email sent, a payment captured) needs its own dedupe key at the provider. Not instant propagation: the relay adds latency - poll interval plus queue time; end-to-end latency was not measured here, so size the UX for a visible delay or use change-data-capture (Debezium reading the WAL). Not ordering: events can arrive out of order, and the demo's consumer applies "published" unconditionally; sequence numbers let a consumer detect and reject stale events, they do not enforce anything by themselves. Not system-wide atomicity: the transaction covers the business row and the outbox row only; everything downstream is eventual. Not free: retention, cleanup, relay monitoring (alert on relay lag, the age of the oldest unpublished row), and event schema care. The demo's relay is a single unclaimed loop; concurrent relays would double-post pending rows. Two correct fixes: hold one claim transaction across the post (a database lock while you wait on the broker), or split claim from post with a persisted claim (lease column + reaper). Either way the mark happens after the post and the duplicate window remains. And when one database with no events or projections is all you have, a plain UPDATE is fine - reach for the outbox when a lost or phantom event would make two truths.
